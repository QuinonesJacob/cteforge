# 0027 — Configurable roles, personal access tokens, per-token tool access

Status: accepted · 2026-11-17 · implemented 2026-11-17 · amends ADR 0007, ADR 0018 (roles,
tokens, agent verify), DESIGN §6, §9, §14, §18

## Context
- Roles are fixed (viewer < contributor < approver < admin) and a user has one token.
  Teams want a narrow agent ("support bot: search + run only") without inventing a role,
  and want that enforced by cteforge itself, for every client, not by each MCP client's
  permission prompts.
- Admin work (users, roles, access) is the daily load an admin agent should take on.
- Tokens are the access key for MCP and the API. cteforge is self-hosted with no central
  authorization server, so OAuth would need each deployment to provide sign-in first.

## Decision

### Roles are configurable; the role is the ceiling
- An admin manages roles in Settings → Roles. Each role has
  - **Allowed**: every tool/action the role may ever use (the ceiling), and
  - **On by default**: what a new token for that role starts with.
- Built-in roles (viewer, contributor, approver, admin) ship as editable defaults; admins
  may create custom roles. `admin` always keeps user/role/settings management.
- A token's tools are a subset of its user's role's Allowed list. Nobody, admin included,
  can give a token a tool its role does not allow; to get more, change the role.

### Personal access tokens (GitHub-style)
- A user has **many named tokens** ("Claude Code", "Cursor", "CI"). Each has: a name, a
  prefix (`cfg_pat_…`, so secret scanners can recognize leaks), created/last-used times,
  an optional expiry, and its own tool list (mode **follow role** = the role's On by
  default plus/minus explicit choices, new tools included automatically; or **only these**
  = a fixed list, new tools stay off).
- A token is **shown once**, at generation; cteforge stores only its SHA-256 hash and can
  never show it again. Lost → generate a new one, revoke the old one.
- People generate their own tokens in Settings → My tokens. Tokens for agent users are
  generated by a **human** admin. **No tool call ever returns a token** (MCP or any
  agent-held token): agents never see tokens.
- Revoking or expiring a token takes effect on the next call.

### Enforcement in services, visible in MCP
- Tool access is checked in `services` (`auth.require`, next to the role check), so the
  same token gets the same answer over MCP, the HTTP API and anything else; the API is
  not a way around MCP's tool list.
- MCP `tools/list` is filtered per token: an agent never sees a tool it cannot use. A call
  to a hidden tool is refused (PermissionDenied) and audited.
- Write tools carry MCP annotations (`readOnlyHint: false`, `destructiveHint` where it
  applies) so clients like Claude Code can still ask the person before calling them.

### Admin agents
An agent-kind user with the admin role may, through MCP:
- create users (human or agent) — **without** receiving a token; a human admin issues it;
- change the role and tools of users who are not admins;
- deactivate users who are not admins and revoke their tokens;
- create and edit roles other than `admin`;
- approve, reject and **verify** (this reverses ADR 0007 / 0018's "agents never verify"
  for the admin role only).

Human-only, always: seeing any token; anything that touches an admin user (role, tools,
deactivation, tokens); granting the admin role; editing the admin role.

### Verify
- Human users with verify in their role (approver, admin, or a custom role) may verify in
  the GUI, API or MCP.
- Agent-kind users may verify **only when they hold the admin role**; no other role can
  grant verify to an agent (the Allowed list ignores verify for agent-kind users).
- Four-eyes still holds with **no admin exemption for agents**: an agent admin never
  approves or verifies a proposal or version it authored any part of (ADR 0018 addenda).
- `verified_by` records the actor and its kind; the GUI and `get_definition` show
  "verified by <name> (agent)" so people can tell, and the Library can filter on it.

### MCP review and admin tools (visible only when allowed)
- Review: `list_proposals` (read), `review_proposal` (write: approve | reject | verify).
- Admin: `list_users` (read: users, roles, token names/last-used — never token values),
  `manage_user` (write: create · set role · set tools · deactivate · revoke token),
  `manage_role` (write: create · edit Allowed / On by default).

### Sign-in roadmap (direction, not built now)
1. Now: tokens as above; the GUI keeps signing in with a token.
2. Later, optional: browser sign-in for the GUI through the company's identity provider
   (OIDC: Okta, Google, Entra, Keycloak), configured by each deployment.
3. Later, optional: MCP OAuth with cteforge as its own authorization server (the MCP
   Python SDK's `mcp.server.auth`), reusing step 2's sign-in, so a person connecting
   Claude Code clicks Authorize. Tokens remain for agent users, CI and scripts (no
   browser), and for teams that skip steps 2–3.

## Consequences
- Narrow agents are a role/token setting, not code; every surface enforces it.
- Store changes: roles table (allowed / defaults), tokens table (many per user, metadata,
  tool list), user `active` flag; existing single tokens migrate to one token named
  "default" following the role.
- "Verified" can now mean an admin agent verified it; the label shows which, and four-eyes
  still blocks self-verification.
- Admin agents can lock out non-admin users; admins and tokens stay under human control.

## Addendum (2026-11-17): implementation model
- **The permission unit is the tool.** `domain` defines a `Tool` catalog (one name per
  operation; MCP tools use the same names): use — `search`, `get_definition`,
  `compile_and_run`, `check_and_run`, `describe_tables`, `list_joins`, `list_recipes`
  (until ADR 0026 removes it); build — `parse_query`, `propose_definition`,
  `revise_definition`, `propose_join`, `propose_recipe` (until 0026); review —
  `list_proposals`, `review_proposal` (approve / reject), `verify`; admin — `view_audit`,
  `list_users`, `manage_user`, `manage_role`, `manage_settings`. Every use-case requires
  exactly one tool (`services/auth.require(user, Tool.X, target?)`); HTTP endpoints map to
  the tool of the use-case they call (e.g. `GET /proposals` → `list_proposals`, export →
  `get_definition`, import → `propose_definition`, search-index rebuild →
  `manage_settings`, library-wide revalidate → `review_proposal`). The old `Action` /
  `ROLE_MINIMUM` table is replaced.
- **Role** (store table `roles`): `name` (Ident), `description`, `allowed` (tools),
  `defaults` (tools, ⊆ allowed), `review_all` (bool), `builtin`. Built-ins are seeded with
  today's behaviour: viewer (use tools + `list_proposals`), contributor (+ build tools +
  `review_proposal` with `review_all = false`: owners approve changes to definitions they
  own, as today), approver (+ `review_proposal` with `review_all = true`, `verify`,
  `view_audit`), admin (every tool, always; its `allowed` cannot be edited; its
  `defaults` only by a human admin). Admin tools (`list_users`, `manage_user`,
  `manage_role`, `manage_settings`) can only be allowed in the admin role. A role in use
  cannot be deleted.
- **Token** (store table `tokens`): `id` (uuid), `user_name`, `name`, `prefix` (first 12
  chars, shown in lists), `token_sha256` (unique), `created_at`, `created_by`,
  `last_used_at` (updated at most once a minute), `expires_at?`, `revoked_at?`,
  `tool_mode` (`follow_role` | `only`), `include` / `exclude` (tool lists). Format
  `cfg_pat_` + 43 URL-safe chars. Effective tools = role.allowed ∩
  (follow_role: (role.defaults ∪ include) − exclude; only: include), then minus `verify`
  for an agent user whose role is not admin. Authentication fails (same generic 401) for
  an unknown, revoked or expired token or an inactive user.
- **Users** gain `active` (deactivated users cannot authenticate); `role` becomes a role
  name (the built-in names keep their values). The legacy `users.token_sha256` column is
  no longer used to authenticate: on first open, each user's existing hash becomes a
  token named `default` (follow_role), so existing tokens keep working.
- **The acting user carries its effective tools** (resolved in services/auth at
  authentication); policy in trust/ stays pure and checks membership. A `User` built
  without tools (tests, the CLI before a store lookup) falls back to its built-in role's
  defaults.
- **Surfaces**: HTTP/MCP over HTTP → the bearer token's tools. stdio MCP → `CTEFORGE_TOKEN`
  when set (that token's user and tools), else `CTEFORGE_USER` with its role's defaults.
  CLI and auth-off HTTP (a person at the machine) → the role's allowed tools.
  MCP `tools/list` shows only the effective tools; calling another is refused and audited.
- **Who may mint a token**: never an agent-kind caller, on any surface (the endpoint
  refuses; no MCP tool exists). A human mints their own; a human admin mints for any user.
  Revoke: own tokens; a human admin any; an agent admin only for non-admin users.
- **Agent admins** (agent kind + admin role): may create users (human or agent; no token is
  returned), change role / tools / active of non-admin users, revoke non-admin users'
  tokens, create and edit roles other than admin, approve / reject (including changes to
  verified definitions) and verify. They may not: give anyone the admin role, touch an
  admin user, edit the admin role, see or mint tokens. The four-eyes rule applies to
  agent admins with no exemption. `verified_by` and proposal decisions record the actor
  kind; cards show it.

## Addendum (2026-11-17): as built
- Store schema version 2: `roles`, `tokens`, `users.active` (added to existing databases
  by an explicit, idempotent `ALTER TABLE`). Opening a version-1 database migrates each
  user's token hash to a token named `default` (follow_role) once, during the 1 → 2
  upgrade; a version-1 cteforge refuses the upgraded database. New users get a random,
  never-shown value in the legacy `users.token_sha256` column, which authenticates nothing.
- Use-case → tool, beyond the addendum's examples: `count_proposals` and
  `get_proposal` → `list_proposals`; `withdraw` → the build tool of the proposal's kind;
  `revalidate(ids)` → `compile_and_run`, library-wide `revalidate()` → `review_proposal`
  with `review_all` (as before: approvers and admins); `list_roles` → `list_users`;
  rename → `revise_definition`; own tokens (list, mint, revoke, set tools) need no tool.
  Recipe and join proposals are approved with `review_proposal` + `review_all` (they have
  no owner). Built-in roles cannot be deleted (they can be edited).
- No self-escalation or persistence through self-service (security review): when a call
  authenticated by a token mints or reconfigures a token of its OWN user,
  - the new token's tools must be ones the calling token holds (a narrow token handed to an
    agent cannot be turned into a broad one);
  - a calling token with an expiry only mints tokens that expire no later (a 1-hour token
    cannot leave a permanent one behind);
  - an `only` calling token cannot create, or switch a token to, `follow_role` (which
    would gain the role's future defaults);
  - the new token records the calling token as `parent_token_id` (store column, added to
    existing version-2 databases by an idempotent `ALTER TABLE`), and revoking a token
    revokes all its descendants in one transaction. A parent's expiry is not cascaded
    beyond the expiry cap above. Consequence: to replace a token, generate the new one
    from another session (or the CLI, which has no token) before revoking the old one.
  The acting user carries the calling token's id, expiry and mode (`GET /me` shows them;
  None for the CLI, auth-off HTTP and stdio without `CTEFORGE_TOKEN`, which are a person
  at the machine and unrestricted). Tokens minted for OTHER users are neither capped nor
  linked.
- `manage_user` is effectively root for a human: it mints tokens for any user (admins
  included) and creates admin users, so a token holding it is as powerful as the admin
  role. This is by design (ADR 0027: human admins manage access); give it only to admins
  and keep such tokens short-lived. Agents holding it are limited as above (no tokens, no
  admin users).
- A `compile_and_run` final `select` that reads raw tables (or table functions) is
  exploratory SQL: it needs the `check_and_run` tool as well (PermissionDeniedError,
  recorded as a rejected compile_and_run), so a token without `check_and_run` cannot run
  arbitrary SQL through `select`. A `select` over the aliases only needs
  `compile_and_run`.
- `create_user` by a human admin over the API/CLI still returns a `default` token once
  (convenience); over MCP (`manage_user create`) and for agent callers it never does.
- An MCP call to a hidden tool is refused before the tool runs and audited as an `admin`
  event (`op=tool_refused`, outcome rejected). `review_proposal` is shown to tokens holding
  `review_proposal` or `verify`.
- `verified_by_kind` on the definition card is looked up from the users table (a user's
  kind never changes); proposals store `decided_by_kind`.
- ADR 0026 (implemented 2026-11-18) removed `list_recipes` and `propose_recipe` from the
  catalog; the store migration strips them from stored roles and tokens. The raw-table
  gate above (a final SELECT over raw tables also needs `check_and_run`) applies to the
  stored final SELECT of every composed definition used — verified or not, nested too —
  and to proposal checks and revalidation of a composed definition, which run its query.

## Addendum (2026-11-17): security re-review
- Functions that read a table / schema by NAME or run a SQL string have no table reference
  for the raw-table gate to see, so they are refused as not read-only in every final
  SELECT and definition (compose.checks `_SIDE_EFFECT_FUNCTIONS`): Postgres
  `table_to_xml*`, `schema_to_xml*`, `database_to_xml*`, `cursor_to_xmlschema`, `ts_stat`
  (joining `query_to_xml*` / `dblink`), ClickHouse `joinGet` / `joinGetOrNull`.
- Known, accepted: narrowing a parent token does not narrow tokens it minted earlier (only
  revoking cascades); a human token holding `manage_user` is effectively root (by design).
